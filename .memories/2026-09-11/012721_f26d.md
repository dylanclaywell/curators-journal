## Phase 4b done — quest store wired, and a real bug it exposed

Handoff point. **Next slice is 4b′: export/import**, not the UI. Reason below.

### What landed (commit d226f00)

`src/stores/quests.ts` — the seam every quest panel goes through:

- **`ensureReady()`** loads the dataset *and* levels in one call. Views must use this,
  not `ensureDataset()` alone.
- `statuses` (`Map<id, QuestStatus>`), `plan`, `questPoints`, `completedCount`,
  `levelsKnown`, `awaitingLevels`
- `cycleProgress(id)` — todo → doing → done → todo, one tap
- `toggleGoal` / `addGoal` / `removeGoal`
- Dataset and user data persist under **separate keys** (`quests:progress`,
  `quests:goals`) so regenerating the dataset can never touch what was typed.
  Progress stores only non-default states, so `todo` is the absence of an entry.

### The bug, because it teaches the rule

The user reported: set a username in Stats, then the Quests panel still says "add your
username" on a fresh load — and tabbing to Stats and back fixes it.

Cause: the hiscores store was **inert unless StatsView had mounted**, because that view
seeded the only snapshot. Fix: **`hiscores.ensureLoaded()`** hydrates from settings +
cache, so any panel can have levels. `App.vue`'s comment claiming a shell-level handler
would be inert is now corrected — that constraint is gone, only the bundle one remains.

Rule for future panels: **never depend on another panel having mounted first.**

Second half of the same bug: the panel conflated "no username set" with "levels still
loading", so it told the player to do something they had already done. Hence
`levelsKnown` vs `awaitingLevels` as separate states.

### Verified in a browser, not just reasoned about

Dev server + Chrome: set Lynx Titan in Stats, then **hard-navigated** to `/quests`.
Reads `84 of 214 quests startable now` immediately, no console errors. That 84 matches
what the Node engine harness independently reports for a maxed account — two unrelated
paths agreeing.

### Also fixed

`evaluateQuest` totalled quest points for every quest when only 13 gate on them —
O(n²), ~46k iterations per recompute on a tablet. Now 0.16 ms for a full 214-quest
sweep, behaviour unchanged (73 startable on a fresh account, before and after).

### Why 4b′ (export/import) jumps the queue

`persist.ts` and CLAUDE.md both called export "the real safety net". **It was never
built.** The quest store is the first thing holding unrecoverable data, and Safari
evicts IndexedDB after ~7 days idle for non-installed sites. Building UI that invites
hand-entering 214 completions before the safety net exists is the wrong order. Both
false claims are now corrected in place rather than left to mislead.

Scope: `quests:progress`, `quests:goals`, `settings` — everything hand-entered. Nothing
fetched; cached hiscores restore themselves.

### Invariants to preserve
- Neither the dataset nor localForage may enter the entry chunk. After `npm run build`,
  grep the `index-*.js` named in `dist/client/index.html` for `cooks-assistant` and
  `localforage` — both must be absent; the dataset should be its own ~108 KB `quests-*.js`.
- Ids derive from wiki titles, so a page rename orphans a completion.
