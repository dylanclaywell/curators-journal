## Recipe for Disaster resolved, and Quest Helper prior art recorded

Two follow-ups to the Phase 3 source spike, both now in ROADMAP.md.

### Recipe for Disaster: subquests are first-class, parent is a display label

The open question from the spike is closed. RFD has 12 pages in the canonical
inventory: a parent, ten subquests, and a `/Full guide` walkthrough. Decision:
**ten subquests become real dataset entries; the parent and `/Full guide` are excluded.**

Evidence, most decisive first:

1. **`Monkey Madness II` requires `Recipe for Disaster/Freeing King Awowogei`
   specifically.** A composite RFD entry would force the claim that MM2 needs all ten
   subquests — reporting a startable quest as blocked. Same invisible-wrongness that
   disqualified Wise Old Man as a level source.
2. **The subquests already form a clean graph:** eight middle subquests each require
   `Another Cook's Quest`; `Defeating the Culinaromancer` requires all eight. A diamond,
   and exactly the structure the dependency-ordered queue exists to handle.
3. **The parent double-counts quest points.** Parent reports `qp=10` plus the union of
   all 14 skill requirements; each subpage carries `qp=1`. Counting both gives 20. This
   is load-bearing: 13 quests gate on total quest points, including Dragon Slayer II
   (200) and While Guthix Sleeps (180), so inflation would wrongly unlock the top tier.

Keep `"Recipe for Disaster"` as a **display group** so the UI can render one collapsible
row of ten, matching the in-game journal. `Infobox Quest` has a `series` param, so the
same grouping generalizes (Elf series, Desert Treasure) — display only, never a dependency.

**Unexpected payoff:** the ~52 unparsed requirement lines flagged as the spike's messiest
finding were *all on the parent page*. Dropping it eliminates nearly all of them, so this
decision makes the generator simpler instead of adding a special case.

### Prior art: RuneLite's Quest Helper (researched, not adopted)

Checked the source rather than assuming, because it superficially looks like it solves
our problem.

- **It reads quest _progress_ from the running game, not requirements.**
  `quest.getState(client)` returns not-started / in-progress / finished plus a step
  number, straight from server-side per-quest progress values.
- **Requirements are 100% hand-written.** 1,075 files, 728 Java, **zero data files** —
  no JSON/CSV/YAML, nothing wiki-derived. Requirements are literal code
  (`new SkillRequirement(Skill.SLAYER, 18)`) across 462 quest classes.

Conclusions worth keeping:

- **Hand-entered completions in StageScape are structural, not a shortcoming.** Quest
  Helper gets state free *only* because it runs inside the client. We can't — hiscores
  don't expose quest state, Fan Content Policy §6.1.2 forbids third-party clients, and
  the second-screen premise means no desktop plugin is running. Progress is the only part
  the game gives away free; nobody gets requirements free. Reinforces why export/import matters.
- **Their hand-writing is evidence about scope, not about the wiki.** They need per-step
  items, dialogue and tile locations that no wiki field carries; once writing that,
  hardcoding requirements is free. Costs them a code release per quest. Our need is
  requirements-for-ordering, which is the part the wiki structures well. Wiki data
  supports a *planning* tool; a *guided walkthrough* would be a far bigger lift.
- **Banked as a possible third cross-check:** BSD-2-Clause, actively maintained,
  requirements curated against the live game rather than the wiki validating itself.
  Extraction means parsing Java. Flagged in ROADMAP to settle NOTICE.md attribution
  before using any of it.
