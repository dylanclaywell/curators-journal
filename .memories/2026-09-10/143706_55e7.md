## Phase 2 data layer complete (slices 2a + 2b)

`f299aeb` worker route + parser, `67e3d2d` client store. Stats panel does a real lookup end to end.

### Discovery: OSRS has 24 skills, not 23

Verifying against a live `index_lite.json` before writing the parser caught **Sailing** at id 24, missing from `SKILL_NAMES`. The grid would have silently omitted a real skill. Parser now matches **by name, not array position**, so the next mid-list insertion can't shift everything.

Also live-verified: the two arrays encode "unranked" differently — skill `{rank:-1, level:1, xp:0}` (only rank absent), activity `{rank:-1, score:-1}` (both absent). And there's a top-level `name` giving Jagex's canonical capitalisation.

### The API question, settled

We call exactly one upstream: `https://secure.runescape.com/m={module}/index_lite.json?player={name}`. Official Jagex domain but **undocumented** — no published contract or stability guarantee (hence Sailing appearing unannounced).

**Rejected Wise Old Man** as the levels source: it's snapshot-based (`GET` returns `latestSnapshot`, needs a `POST` to refresh), so it can be weeks stale. Disqualifying when quest eligibility is computed _from_ levels — it'd be wrong exactly where the app claims value. WOM stays a candidate _additively_ later for gains/history/name-changes, which it does well and we don't need yet.

**Rate limits:** Jagex publishes none; they declined to confirm via support ticket (per osrs-lib author), community estimate ~15/min with IP-block risk on bulk. WOM documents 20/min, 100 with a key.

### Freshness and rate limits are ONE constraint

User's correction, and correct: freshness is only obtainable by requesting, requests are capped, so the cap is a ceiling on freshness. **The Worker's cache TTL is the only knob.** At 60s with one player that's 1 upstream req/min ≈ 7% of a pessimistic 15/min budget — ~15× headroom, so the limit is _not_ binding for a single user. It only bites at multiple accounts (a clan feature would change this).

Real ceiling is probably **upstream lag** — hiscores don't update live and the interval is unmeasured. Polling faster than that buys nothing. User to measure: refresh repeatedly while training, watch when XP moves. TTL stays 60s until then (user's call, confirmed).

### Design ideas banked for Phase 4

- **Spend freshness where it changes an answer**: eligibility only flips when a level crosses a requirement boundary, and we uniquely know those boundaries. Demand-driven cadence — eager when one level from an unlock, lazy otherwise.
- The _game_ notifies level-ups, not us, so staleness cost is low; manual refresh covers the rest.
